# Revision 0.1.0-dev.9 — Flashforge cloud device workflow

Status: needs user testing.

The Flashforge Device page combines cloud printing and job monitoring with:

- Pause, resume and cancel for the current cloud job. Cancel asks for confirmation
  with the printer and filename. Buttons require a fresh live observation and an
  eligible printer state; resume is enabled only once the printer reports paused.
- Current filename, layer count, elapsed/estimated remaining minutes and a progress bar.
- A manual Refresh live status button and the existing monitoring checkbox.
- Choose printer directly on the page, using the combined Bambu/Flashforge picker.
- A compact printer list and a vertically scrollable page for smaller windows.

The original cloud-send workflow, dual account sessions, profiles, firmware
indicators and Bambu integration remain available. No LAN connection is needed.
This revision does not replace the Bambu networking plug-in or unlock its
restricted filament/camera controls.

## Try it

Close the running slicer and open Launch-Slicer.cmd. Existing accounts/settings
remain in revision 1's data folder; no new source ZIP download is required.

1. Open the Flashforge Device page. Choose your Adventurer 5M and enable cloud
   monitoring, or press Refresh live status. Check filename, layers and progress
   during a print. Time values are vendor-reported estimates, not guarantees.
2. During a suitable test print, press Pause print. Wait for the printer status
   to report paused, then press Resume print. A sent-command message alone is not
   proof the printer responded.
3. If you have a disposable test print, try Cancel print and its confirmation.
   This stops that physical print; Cancel sending is the separate upload control.
4. Use Choose printer to switch to Bambu and back. Check normal cloud submission
   and both account sessions as you use the build.

Cloud controls also work on the current job started elsewhere, provided the cloud
reports its job ID. If no job ID is reported, buttons remain disabled. A changed
job, stale account membership or incompatible status blocks the request. The
worker checks state before and again after connecting. The printer may still
change state after that final observation; the explicit job ID narrows the action
to the job selected by the user, subject to the vendor's implementation.

## Delivery and failure handling

Commands follow the pinned Orca-Flashforge `ComWanConn::sendJobCtrl` ABI:
`FNET_CONN_WRITE_JOB_CTRL`, device topic, QoS 1, current job ID and action
`pause`, `continue` or `cancel`. Delivery success only means the SDK accepted the
send. There is no explicit printer acknowledgement in this ABI. The existing
5-second live poll confirms subsequent state; it runs only while monitoring is
enabled and the page is visible. Controls enable monitoring after an action.

Commands run on the same sequential account worker as refreshes/uploads. Account
sign-in changes cannot run concurrently. A disconnect, exception or uncertain send
never triggers an application-level command replay. MQTT QoS 1 can itself redeliver
a message; application dispatch exactly once is not an end-to-end exactly-once
guarantee. SDK callback-thread teardown remains a proprietary implementation
assumption shared with the prior working cloud-print adapter.

Development validation is limited to build/source/package checks and mocked
identity, lifetime and connection fault checks that are difficult to exercise
with hardware. Appearance and actual printer command acceptance require user
testing. No real printer commands or sign-ins were performed by tools.

Revision 8 remains available through Manage-Versions.cmd for rollback. All
revisions share the original settings folder; rollback changes the executable.
